About User-Agent strings

The User-Agent HTTP header is sent by browsers and other clients with every request. Servers use it for analytics, feature detection, content negotiation, and crawler identification. Unfortunately the format has grown into a tangle of historical compatibility tokens — every major browser still claims to be Mozilla/5.0 for backwards reasons rooted in the 1990s browser wars.

Anatomy of a typical UA

A modern desktop UA usually looks like:

Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36

Decoded: Mozilla/5.0 is a legacy compatibility token. (Windows NT 10.0; Win64; x64) describes the OS and CPU. AppleWebKit/537.36 (KHTML, like Gecko) identifies the rendering engine ancestry. Chrome/124 is the actual browser, and the trailing Safari/537.36 is more legacy padding.

How this parser works

It runs entirely in your browser using a focused set of regular expressions tuned for the browsers, engines, and operating systems you actually encounter in production traffic — Chrome, Firefox, Safari, Edge, Opera, Samsung Internet, common mobile WebViews, and major bots like Googlebot and Bingbot. Nothing is sent over the network.

Common uses

  • Debugging analytics events that report a wrong browser or OS
  • Reproducing user reports by matching their exact device and version
  • Verifying that crawlers and bots are correctly identified
  • Inspecting your own UA when testing feature flags or A/B targeting

A note on accuracy

User-Agent strings can be spoofed and many browsers now ship reduced UA values, pushing real device data into the newer Sec-CH-UA client-hint headers. Treat parsing results as a strong hint, not an identity. For server-side fingerprinting that has to be reliable, combine UA parsing with client hints and, where appropriate, JavaScript feature detection.
